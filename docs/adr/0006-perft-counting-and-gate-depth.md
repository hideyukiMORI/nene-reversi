# ADR 0006 — perft はパスを 1 手と数える出典に合わせ、release 構成で深さ 11 までゲートに回す

- 状態: 受理
- 日付: 2026-10-26
- Issue: #3
- 影響する規則: QLT-001 / QLT-002 / QLT-008 / SWF-008 / SWF-016

## 文脈

リバーシの perft は、パスを 1 手と数えるか・途中で終局した手順をどう数えるかで値が変わる。期待値は一次資料から写し、
出典の数え方を書き、実装をそれに合わせる必要がある。どの深さまでゲートで回すかは速さを測ってから決める。深さを黙って下げない。
ADR 0002 は、最初のテスト target が入る PR で `swift test` をゲートに結線すると決めていた。

### 出典（2026-10-26 に取得）

| 出典 | 中身 | 数え方の手がかり |
| --- | --- | --- |
| OEIS A124004「Number of possible Reversi games at the end of the n-th ply」 | 深さ 0〜21 の値（`%S` `%T` `%U` 行）。深さ 19〜21 は Dominic Hofer が足した | 本文には書かれていない |
| Dominic Hofer の ReversiPerftCUDA（GitHub `PanicSheep/ReversiPerftCUDA`）の `Perft/Perft.cpp` | OEIS と同じ値の表と、数える関数 `BasicPerft::calculate` | 深さ 0 なら 1。合法手が無ければパスした局面を**深さを 1 減らして**数え、相手にも合法手が無ければ 0 |
| Edax 4.6.13 の `-count games 17` の出力（作者が 2026-06-04 に Codeberg の Issue に投稿・URL はリポジトリ名に登録商標を含むので書かない） | 深さ 1〜17 の `moves`・`passes`・勝敗の列 | `moves` の列が OEIS と深さ 1〜17 で全部一致する。`passes` は深さ 9 で 24、深さ 11 で 576。勝敗の列（`losses`）は深さ 10 で 228、深さ 11 で 356 と、深さ 10 から終局が現れる |

OEIS の値と Edax の値は独立に計算されたもの（Brobecker・Byrne・Hofer と、Edax の作者）で、深さ 1〜17 で一致する。

### 実測（WSL2 Ubuntu・Swift 6.4.1・2026-10-26）

初期局面から深さ 1, 2, … を順に数え、公表値の列と比べる（`PerftTests.matchesPublishedCounts`）:

| 構成 | 回した深さ | テストの所要（壁時計） |
| --- | --- | --- |
| release（`swift test -c release`） | 1〜11（計 240,289,780 手順） | 5.0 秒（`make check` の中では 6.1 秒） |
| release（`swift test -c release`） | 1〜12（計 2,180,169,448 手順） | 41.0 秒 |
| デバッグ（`swift test`） | 1〜11 | 81.4 秒 |

どの深さでも公表値と一致した（深さ 12 の 1,939,879,668 も一致した。1 回だけ測り、ゲートには入れていない）。

## 決定

1. **数え方は Hofer の実装に合わせる**: 深さ 0 は 1。合法手が空（終局）なら、深さが残っていても 0（その手順は深さ N に届かない）。
   パスは 1 手として深さを 1 減らす。ADR 0005 の `legalMoves()` がパスを手の 1 つとして返し、終局で空を返すので、
   perft は「合法手を 1 つずつ適用して深さ 1 減らす」の 1 通りだけで書ける（パス専用の分岐が無い）
2. `make check` の `test` 段は `swift test -c release` を回し、**初期局面の深さ 1〜11** を公表値と比べる。
   深さ 9 と 11 にパス（Edax の `passes` が 24・576）、深さ 10 と 11 に終局した手順（Edax の `losses` が 228・356）が現れるので、数え方の違いがあればここで値がずれる
3. テストは `@testable import` で内部（`flips`・`mobility`）にも触れてよい（SWF-008。release 構成でも効く・ADR 0001 の X-e）
4. 段は安い順に並べ、`test` は規約検査の後ろに置く。`swift test` は `eng/swift-strict.sh` から呼び、SwiftPM 自身の警告も失敗にする

## 強制

- **active**（QLT-001 の一部）: 証明 P48（perft の期待値を 1 つ変えると `make check` の `test` 段が `✘ Test matchesPublishedCounts` で落ちる）
- **active**（QLT-002 の一部）: 証明 P47（ソースの無いテスト target で SwiftPM が警告を出すと `make check` が落ちる）

## 結果

- 合法手生成・反転・パス・終局の数え方を、公表値の 240,289,780 手順ぶんで確かめてから画面と探索に進める
- `make check` の `test` 段は約 6 秒。CI のランナーはこれより遅い可能性がある
- 失うもの: デバッグ構成でしか出ない不具合（`assert` の発火）をテストで見ない。製品コードは `assert` を使わず、欠陥は `precondition` で止める
  （`precondition` は release でも効く）
- 正直に記録しておくこと: perft が見るのは初期局面から届く局面だけで、手で作った局面（パスだけの局面・盤の埋まらない終局など）は
  `PositionTests` が別に見る。初期局面以外の perft の公表値は使っていない（見つけた出典はどれも初期局面だけだった）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 深さ 12 までゲートで回す | 1 回 41 秒で、深さ 11 までの 8 倍かかる。パスと終局は深さ 9〜11 ですでに現れ、深さ 12 で新しい種類の出来事は増えない。測って一致したことはこの ADR に残した |
| デバッグ構成で深さ 11 を回す | 81 秒かかり、毎回のゲートに向かない |
| 深さ 8 か 10 で止める | 深さ 8 まではパスも終局も無く、数え方の違いを検出できない。深さ 10 はパスが 0 で、パスの数え方を値で確かめられるのは深さ 9 の 24 件だけになる |
| パスを数えない（パスした局面で深さを減らさない）数え方 | 出典の値と一致しない。数え方を出典に合わせるという要件に反する |
| 深さ 12 以上は別の重いゲート（CI だけ・夜間）に回す | ゲートは一つ（QLT-001）・CI にしか無い検査を作らない（QLT-005） |
| `-Ounchecked` で回す | 整数の桁あふれと配列の範囲外の検査が消え、製品と違う構成を試すことになる |
