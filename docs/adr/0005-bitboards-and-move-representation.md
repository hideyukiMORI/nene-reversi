# ADR 0005 — 盤は黒と白の 64 ビット 2 枚、手は「升に打つ／パス」の閉じた enum、適用は新しい局面を返す

- 状態: 受理
- 日付: 2026-10-26
- Issue: #3
- 影響する規則: ARC-001 / ARC-004 / ARC-005 / ARC-008 / ARC-010 / SWF-001 / SWF-002 / SWF-004 / SWF-007

## 文脈

盤の表現・手の内部表記・パスの表し方・局面の文字列表現は、それぞれ 1 つに決めて ADR に書く必要がある（PROJECT_LAYOUT 第 3 節・用語集）。
「パスか」「終局したか」を判定する経路も Core に 1 つずつでなければならない（ARC-004）。

材料:

- perft はパスの現れる深さ 9 より深く回したい（ADR 0006）。初期局面の深さ 11 は 212,258,216 手順ある
- 兄弟の NeNe Gambit は盤を `InlineArray<64, Piece?>` にし、bitboard を「ビット演算の表と魔法数が要る」として却下した（Gambit ADR 0003）。
  リバーシの bitboard は飛び駒の魔法数が要らず、8 方向へのずらしとマスク 2 つで書ける
- Swift 6.4.1 の `UInt64` の `<<` はずらす量が 64 以上なら 0 になり、`&<<` は 64 の余りでずらす（ADR 0001 の X-d）。ずらす量は 1・7・8・9 だけなので、どちらでも同じ値になる
- Gambit は `Move` の init を internal にし、Core の外の指し手を `legalMoves()` からしか得られないようにした

## 決定

1. **盤は `Position` の中の `black: UInt64` と `white: UInt64` の 2 枚だけ**。升 `index = row * 8 + column` のビットが立っていればその色の石がある。
   a1 = 0（盤の左上）、h8 = 63。1 行目が上端で、初期局面の黒は d5 と e4、白は d4 と e5（出典の Edax と Hofer の図と同じ向き）。
   2 枚に同じビットが立つ値は作らない（唯一のファクトリ `Position.arranged` の `precondition`）。
   盤の外へのずらしと行の回り込みは `Direction.shift` の 1 か所で消す（右へずらしたら a 列、左へずらしたら h 列のビットを落とす）
2. **手は `Move` の 1 表記**。中身は閉じた enum `MoveKind`（`.place(Square)` か `.pass`）で、反転する石は手に持たず、局面から導く。
   `Move` の init は private で、Core の外の手は `Position.legalMoves()` からしか得られない。升の名前（`d3` など）への変換は Render が持つ
3. **パスか・終局かを決める経路は `Position.legalMoves()` だけ**。手番の側に打てる升があればその升への手（a1 から h8 の順）、
   無くて相手に打てる升があれば `.pass` 1 つ、両者とも無ければ空。`Position.status` は「合法手が空なら終局」をこの関数から導き、石の数で勝敗を決める
4. **手の適用は新しい局面を返す**（copy-make）。`Position.applying(_:)` は元の局面を変えない
5. **局面の文字列表現は「盤の 64 文字・空白 1 つ・手番の 1 文字」**。盤は a1, b1, …, h8 の順に黒 `X`・白 `O`・空き `-`、手番は `X` か `O`。
   初期局面は `---------------------------OX------XO--------------------------- X`。読み書きは `PositionCodec` の 1 経路だけで、
   読めない文字列は閉じた enum `PositionDecodeRejection` の理由で返す（例外にしない）。
   盤の中身が実際の対局で現れうるかは見ない（パスや終局の局面を手で作ってテストで読むため）

## 強制

- **planned**（ARC-001）: 盤の表現と手の表記を混ぜないことは、型が 1 つしか無いことで成り立つが、2 つ目を作らないことはレビュー事項
- 補助（active）: `Move` の init が private なので、Core の外で手を作れない（コンパイラ・M4-b と同じ仕組み）。
  `MoveKind` と `PositionStatus` は閉じた enum なので、分岐の漏れはコンパイルで落ちる（M1-a）
- テスト（`make check` の `test` 段・ADR 0006）:
  - 合法手の升は「反転が 1 つ以上ある空き升」とちょうど一致する。打てる升（`mobility`）と反転（`flips`）は別の経路で計算しているので、片方の誤りはもう片方とずれて落ちる
  - h1 と a2 のように 64 ビットでは隣り合うが盤では隣でない升の間で、石を挟まない
  - 角からの 3 方向の同時反転・盤の端や空き升で終わる列は反転しない・パスしかできない局面・盤の埋まらない終局・盤の埋まった終局の勝敗
  - 1 局を終局まで進め、1 手ごとに石の総数がちょうど 1 増え、反転した数だけ手番側が増え相手が減る（パスでは変わらない）。局面の文字列表現を読んで書くと同じ文字列に戻る

## 結果

- perft は release 構成で深さ 1〜11（計 240,289,780 手順）が約 5 秒（ADR 0006）
- 局面は 2 つの整数と手番だけの値なので、Engine の探索は局面をそのまま引数に渡せる。可変な盤を戻す処理（unmake）が要らない
- 失うもの: 升ごとの石を読むのにビットの検査が要る。Render は `Position.disc(at:)` を 64 回呼ぶ（1 フレームに 1 回なので問題にならない）
- 正直に記録しておくこと:
  - `applying` に渡された手は、升が空いていること・挟める石があること・パスなら本当にパスしかできないことを `precondition` で確かめ、
    外れたら欠陥として止める（期待される失敗ではない）。`Move` は局面に結び付いていないので、別の局面の `legalMoves()` から得た手を渡すことは
    型では防げない。Engine は手を選んだ局面にだけ適用する
  - 文字列表現の `X` / `O` は出典（Hofer・Edax）の表記に合わせた。画面に出す記号ではない（石は色のブロックで描く・FR-07）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| `InlineArray<64, Disc?>`（Gambit と同じ升ごとの配列） | 合法手と反転を升ごと・方向ごとの繰り返しで求めることになり、perft の深さ 11 以上が遅くなる。リバーシの bitboard は魔法数が要らず、Gambit が却下した理由が当てはまらない |
| 手番の側と相手の側の 2 枚（色ではなく「自分・相手」で持つ） | 1 手ごとに 2 枚を入れ替えるので速いが、`disc(at:)` が手番によって意味を変え、Render とテストが読み違えやすい。速さは色で持っても足りた |
| パスを `Move?` の nil で表す | nil に「パス」という 2 つ目の意味を持たせることになる（SWF-004）。閉じた enum なら分岐の漏れがコンパイルで落ちる |
| パスを `legalMoves()` に入れず、呼ぶ側が「空ならパスか終局か」を判定する | パスか終局かを判定する経路が呼ぶ側ごとに増える（ARC-004）。perft もパスを 1 手として数えるので、手の列に入っているほうが数え方と合う |
| 手に反転する石を持たせる | 同じ情報を局面と手の 2 か所に持つことになる（ARC-004）。合法手を並べるだけの葉で反転を計算する無駄も出る |
| make / unmake（可変な盤を戻す） | 中核に可変な区画を増やすことになる（ARC-005）。値型の copy-make で perft の速さが足りた |
| 局面の文字列表現に手数やパスの履歴を入れる | 合法手と終局は盤と手番だけで決まる。履歴は 1 局の値（Phase 3 の手順 2）が持つ |
